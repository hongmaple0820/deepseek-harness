# Agent Note: 会话注意力系统

Status: proposed

[English](2026-11-15-session-attention-system.md) | 中文

## Problem

会话状态表是一个被动展示面：一个会话完成、失败，或开始等待审批/提问时，只在侧栏行上做个标记，要知道它就得去看那里。用户在应用内、正在另一个会话里工作时，那枚徽标就是全部信号——没有任何东西到达用户注意力真正所在的地方，也就是他们正在输入的输入框旁边。用户离开时，[桌面通知提案](2026-11-15-desktop-notifications-for-background-sessions.zh.md) 能触达操作系统，但在场与缺席需要不同的展示面，而任务栏与托盘今天完全不承载聚合状态。

触发所需的全部事实都已在客户端的会话状态表里：运行状态、生效中的待处理交互、自然完成未读与失败（[session reading state](../../implemented/feature/2026-10-23-session-reading-memory.zh.md)）。缺的是从该表派生的转换事件流，以及按各自在场条件消费它的展示面。

## Proposal

### 触发

ui-session-status 客户端面里的一个注意力监视器订阅状态表，按「转换」而非「状态」发事件：某会话的自然完成未读由假变真发出 `completed` 或 `failed`，某会话出现待审批或待提问发出 `approval` 或 `question`。触发规则沿用 [桌面通知提案](2026-11-15-desktop-notifications-for-background-sessions.zh.md) 已陈述的那些：手动未读标记永不通知，可见且聚焦的主视图会话永不通知，委派审批被审批契约排除。监视器与展示面无关——不导入任何 Electron 全局、不认识任何 UI——每个消费方套用自己的在场条件。该提案的监视器升格为这里的共享核心，策略不变。

在场条件按展示面分流。应用内栈只在页面可见且聚焦、且会话不是主视图时触发：用户在场，系统通知保持沉默。系统通知只在页面隐藏或窗口失焦时触发，与其笔记所述完全一致。任务栏与托盘展示面聚合状态、无在场条件，因为徽标与计数是环境态而非打断。不存在追赶：用户离开期间发生的转换，回来时绝不会作为应用内通知补发——侧栏徽标就是追赶面，缺席期间已由系统通知覆盖。

### 应用内注意力栈

新的键控槽位 `workspace.attention`，注册在 shell overlay 下、行级 toast 旁边，渲染一叠通知卡，锚定在输入框卡片上方、与其左对齐、向上堆叠。不复用行级 toast：它是单槽瞬态——新 toast 顶掉前一个、三秒后淡出——而注意力通知要跨会话排队、在审批等待期间驻留、支持手动关闭；两种语义会互相破坏。复用的是 Toast 原语的锚定测量，消息反馈 toast 已经用同样的方法锚定到输入框卡片。

栈按会话保留一条通知——新事件替换该会话的旧通知——最多三张可见卡片，外加一行读作「还有 N 个会话需要关注」的溢出行，点击聚焦侧栏。卡片显示会话显示名、一行类别——完成、失败、等待审批、等待提问——审批类额外一行上下文，含工具名与展示理由，与审批面板相同的信息下限。每张卡片带一个「查看」动作，经 `uiWorkspace.openSession`——与会话列表相同的路径——打开该会话，随后由现有的自动确认清除未读。完成与失败卡片约八秒后淡出；审批与提问卡片永不自动消失。用关闭按钮关掉卡片不会让同一事件重发。

### 快速审批回复

审批卡片增加「允许」与「拒绝」动作，直接调用状态快照携带的 `PendingApproval` 实例上的 `answer()`——与审批面板的 Enter 和 Esc 使用同一个对象与代码路径；不新建审批通道，委派语义不受影响。护栏：上下文行强制存在，「查看」保持主动作，委派审批被排除，提问永不提供快速回复——带推荐选项的结构化选择不能替用户挑一个。回答成功卡片消散；失败则转为错误态并保留「查看」。接受的取舍：一行上下文终究窄于完整审批面板——`allowed-once` 是受限授权，「查看」仍是默认路径，若真实使用中出现误操作，快速回复的设置开关是备好的退路。

### 任务栏、托盘与 Dock

渲染进程计算聚合——有待处理交互或自然完成未读的会话数（手动标记不计）加上每个此类会话的标题与类别——并在变化时经新的类型化 `dshDesktop.attention` 通道推送；不存在轮询。Windows 显示任务栏覆盖徽标，且仅审批事件触发窗口闪烁；macOS 设置 Dock 角标计数，且仅审批事件触发 critical 弹跳；Linux 在启动器支持处设置角标计数，其余静默降级。计数大于零时托盘菜单增加一个「需要关注的会话」区，最多五行，每行经与系统通知点击完全相同的路径打开其会话：显示并聚焦窗口、转发会话 id、在主视图中打开。托盘图标渲染注意力变体，tooltip 追加计数，计数归零时还原。托盘菜单不提供快速回复：菜单项点击即消失、放不下上下文行，跳转是它唯一的动作。

### 设置

General 页一个设置组——应用内注意力提醒、系统通知、任务栏/托盘标记，默认全开——声明方式与聊天偏好相同：config-forms 命名空间加 `settings.general.item` 槽位。系统通知与任务栏开关在浏览器标签页中隐藏。三个都放在客户端 Cordis 设置里，因为触发器与消费方都在客户端；外壳不加自己的设置，遵守 [shell configuration](../../implemented/architecture/2026-10-08-desktop-shell-configuration.zh.md) 的归属规则。

### 与既有笔记的关系

[桌面通知提案](2026-11-15-desktop-notifications-for-background-sessions.zh.md) 拥有系统通知面；其监视器升格为这里定义的共享核心，触发策略不变。[Session reading state](../../implemented/feature/2026-10-23-session-reading-memory.zh.md) 拥有未读记录及其确认；本提案只消费它的流，不取代其中任何部分。[Close-to-background](../../implemented/architecture/2026-09-23-desktop-close-to-background-and-quit-confirmation.zh.md) 的规则不变：关闭窗口本身不发通知。[Shell configuration](../../implemented/architecture/2026-10-08-desktop-shell-configuration.zh.md) 保持设置归属边界。

## Alternatives considered

**复用行级 toast 承载应用内通知。** 行级 toast 是单槽瞬态，顶掉前一个、三秒自动淡出；注意力通知要跨会话排队、在审批等待期间驻留、支持手动关闭。共享槽位会破坏两个展示面，因此栈是兄弟槽位，只复用锚定测量。

**不分在场条件、一律发应用内通知。** 用户离开时应用内通知在回来之前不可见，且与已发出的系统通知重复；用户在场时系统通知是冗余噪音。在场分流让每个展示面只在「自己是唯一信号」的条件下发声。

**回来时补发追赶通知。** 窗口重获焦点时重放错过的转换，每次打开都会先吃一串过期卡片；侧栏徽标已经承载错过的状态，缺席期间已由系统通知覆盖。不做追赶。

**托盘菜单里的快速回复。** 菜单项点击即消失，放不下让快速回复得以安全的上下文行；托盘区改为跳转到会话。

**提问的快速回复。** 待处理提问是带推荐选项的结构化选择；自动挑一个等于替用户作答。提问只提供「查看」。

**Host 侧监视器。** 未读、观看与焦点语义都在客户端；Host 侧监视器复制策略并增加第二条设置路径。与桌面通知提案中的否决理由相同。

**只有徽标、不做应用内栈。** 徽标是被动的；在应用内、正聚焦另一个会话的用户，在他们的注意力位置仍然什么都得不到。栈才是触达他们的展示面。

## Acceptance criteria

- 每次转换恰好一个事件；同一结束回合永不通知两次；手动未读标记、可见且聚焦的主视图会话、委派审批产生零事件。
- 页面可见且聚焦时的完成产生应用内通知、无系统通知；同一完成发生在隐藏时产生系统通知、回来时不补发应用内通知。
- 三个会话先后完成，三张卡片按序堆叠；第四个产生溢出行；审批卡片永不自动消失；「查看」打开会话并经现有确认清除未读；关掉卡片不重发同一事件。
- 快速审批消散卡片、恰好调用一次 `answer()`、同步解决打开着的审批面板；委派审批与提问只显示「查看」。
- 任务栏与 Dock 角标计数等于有待处理交互或自然完成未读的会话数（手动标记不计）；托盘行点击经与系统通知点击相同的路径打开会话；计数归零移除徽标并还原托盘图标。

## Risks

- 并行会话可能爆发：按会话替换通知把栈限制在每会话一卡，三卡上限加溢出行约束视觉成本，静音时段策略继续推迟到真实使用之后。
- 快速审批降低了允许一个工具的摩擦：上下文行、「查看」优先排序、委派排除是护栏，出现误操作时设置开关是备好的退路。
- 渲染进程是触发源：页面崩溃或重载会让全部注意力停止，而 Host 继续运行。接受，与桌面通知提案同一取舍。
- 平台徽标投递各异——Windows 覆盖渲染、macOS Dock 设置、Linux 启动器支持——并静默降级；与托盘和通知工作一样，需要逐平台手工验证。
- 栈在行级 toast 旁边增加了第二个 toast 展示面；槽位边界就是接缝，行级 toast 的行为保持不动。
